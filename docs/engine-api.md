# Engine and MCP API

The React editor and stdio MCP server call one authenticated loopback broker. The broker owns the `ProjectStore`, validated operations, persistence, undo/redo and jobs. Rendering and simulation consume the same saved project contract. There is no separate agent-only mutation implementation. If an MCP request cannot reach its configured loopback broker, the tool error names that local origin and advises checking the editor service; it does not change permissions or restart the service.

## Documents and commands

Projects use `format: "voxshop-project"`, `version: 1`, stable IDs, a monotonic revision, meter units and Y up. Native asset model envelopes use `format: "voxshop-model"`, `version: 1`. Unsupported versions fail instead of being partially imported.

The MCP `project_apply` tool accepts:

```json
{
  "projectId": "my-game",
  "expectedRevision": 0,
  "requestId": "make-prop-001",
  "label": "Generate and place a prop",
  "operations": [
    {
      "type": "asset.generate",
      "id": "crate",
      "name": "Crate",
      "voxelSize": 0.2,
      "recipe": {
        "version": 1,
        "seed": 0,
        "shapes": [{ "kind": "box", "center": [0, 5, 0], "size": [10, 10, 10], "color": 10855845 }]
      }
    },
    {
      "type": "node.put",
      "sceneId": "main",
      "node": {
        "id": "crate-instance",
        "name": "Crate",
        "assetId": "crate",
        "transform": { "position": [2, 0, 0] },
        "components": [{ "type": "collider", "size": [1, 1, 1], "offset": [0, 0.5, 0], "solid": true }]
      }
    }
  ]
}
```

The broker applies the batch to a detached document and validates the final state. Missing assets, hierarchy cycles, dangling rule targets, incompatible equipment and invalid skinning reject the whole batch. Asset deletion is blocked while referenced. Node deletion cascades to its children; external rule references must be removed in the same batch.

Accepted operations: `project.rename`, `asset.put`, `asset.rename`, `asset.delete`, `asset.generate`, `asset.character`, `asset.edit`, `asset.variant`, `equipment.fit`, `world.create`, `world.update`, `world.edit`, `scene.put`, `scene.scatter.create`, `scene.scatter.delete`, `scene.delete`, `prefab.put`, `prefab.delete`, `prefab.instantiate`, `node.put`, `node.delete`, `editor.set`. `asset.put`, `scene.put`, `prefab.put` and `node.put` replace their full record. Use inspection before replacing one, and preserve wanted fields.

`scene.scatter.create` accepts a scene-local group ID, asset ID, signed integer seed, count from 1–1,000, meter-space X/Z bounds, terrain-snap flag, flat ground height, scale range and random-yaw flag. It deterministically creates ordinary editable scene nodes, so agents can inspect, move or delete individual placements after generation. Terrain snapping samples the selected world's generated terrain and sparse edits; bounds must stay inside its finite world extent. The first pass supports static opaque voxel assets with at most 4,096 voxels so the current renderer can batch them; it rejects rigged and glass assets. These nodes use the normal rigid opaque instancing path. `scene.scatter.delete` removes a group and its remaining generated nodes, including descendants parented beneath them. Scatter groups and their source assets survive standalone export.

Reusable prefabs store a project-level scene-node subtree with a declared root, asset references and authored components. The editor can save the selected object and descendants; MCP agents use `prefab.put`. To instantiate one, provide `nodeIds` in the same order as the saved `prefab.nodes` array; each ID must be unique and unused in the destination scene. Internal parent IDs and rule-action node targets are remapped. Optional `position` and `rootName` override the root. `attachmentParentId` preserves the root's local transform when saving a child subtree; placement then requires that parent ID in the destination scene, and that referenced parent must remain present while the prefab is saved. Other scene and catalog dependencies remain by reference and are validated at commit. Placed instances remain linked to the source: replacing a prefab definition updates fields that still match the old source, preserves differing fields as per-instance overrides, adds new source nodes, removes unchanged deleted nodes, and detaches modified nodes whose source was deleted. Deleting a linked node records a per-instance removal override; `prefab.reset` restores source values and removed nodes while preserving root position by default. The editor can update a source from a selected linked instance; the chosen instance becomes the new baseline while other instances keep their differing fields. Keep the prefab root ID stable while instances are linked. `prefab.delete` detaches instances as ordinary editable nodes. Standalone exports strip editor link metadata and omit unused prefab definitions. Version-one projects without `prefabs` load with an empty library. Limits are 1,000 saved prefabs, 5,000 nodes per prefab and 25,000 saved prefab nodes per project.

Reusable prefabs store a project-level node subtree with a declared root, original asset references and components. The editor can save the selected node and its descendants; MCP agents use `prefab.put`. To instantiate one, provide `nodeIds` in the same order as the saved `prefab.nodes` array; IDs must be new and unique in that scene. Internal parent IDs and rule-action node targets are remapped, and optional `position` and `rootName` override the root. An optional `attachmentParentId` preserves the root's local transform when the prefab was saved from beneath a scene parent; placing it requires that parent ID in the destination scene. Other scene-specific references are preserved and validated at commit, so catalog and external node dependencies must exist in the destination. Placed nodes are regular editable nodes; standalone exports omit unused prefab definitions. Projects without `prefabs` load with an empty library. Limits: 1,000 saved prefabs, 5,000 nodes per prefab and 25,000 saved prefab nodes per project.

`asset.generate` through `project_apply` and MCP `asset_generate`, plus `asset.character` through `project_apply`, accept optional `voxelSize` in meters per voxel. It defaults to `0.1` and is bounded to `0.001..100`. The value is stored independently per asset; it changes world dimensions without changing grid coordinates or voxel count. Scene-node scale remains a separate multiplier. Rig joints store absolute voxel-space positions and local bind rotations in radians (default [0,0,0] for older assets); animation key rotations are local deltas composed over the bind pose. Retargeting uses explicit joint pairs and converts each delta through source/target bind-world orientations. Source marker events copy, and key position offsets scale by source/target voxel size to preserve meter motion. For example, a character can be created directly in a `project_apply` batch with `{ "type": "asset.character", "id": "hero", "name": "Hero", "profile": "biped", "voxelSize": 0.2 }`.

### World documents

The Scene Settings form also edits per-scene `background`, `groundColor` and `bounds`. The background colors both the sky and fog; `bounds` is the half-width in meters of the fallback scene floor, and its color/size apply when the scene has no terrain world. The same validated `scene.put` record is used by the editor, MCP agents and standalone exports.

Scenes accept up to 16 authored `objectives`, each shaped as `{ "id", "text", "condition", "requires?" }`. `condition` uses the same variable or inventory comparison as gameplay rules; variable objectives read a missing variable as `0`, while item objectives must reference a catalog item in that scene. Variable comparisons may include `scope: "campaign"` to read shared campaign state; omitted scope remains scene-local. IDs are unique within a scene. Optional `requires` lists unique objective IDs from the same scene; references must exist, cannot point to the objective itself, and cannot form a cycle. An objective is `available` when every prerequisite is complete, and it becomes `completed` only when it is available and its condition passes. Runtime inspection reports `current`, `available` and `completed`; editor Play and standalone HUDs expose locked objectives. `playtest_run` can assert completion by stable objective ID. Exploration, Arena and Survival starters demonstrate goals; Construction remains open-ended. Progress is derived from existing scene/campaign variables and inventory, so there is no second objective save format to keep synchronized. Older scenes default to an empty list.

Scenes may also define up to 32 authored `hud` widgets for game UI. `text` shows fixed copy, `panel` provides an anchored background, `value` binds to a scene or campaign variable, player health or an inventory item, `bar` visualizes one of those numeric bindings, `button` dispatches a gameplay action, `event-button` emits a named rule event, `tab-button` selects a stable `(groupId, tabId)` menu page, and `inventory` renders named stacks with quantities. Variable bindings may include `scope: "campaign"`; omitted scope reads a scene variable. Inventory grids show up to `maxItems` stacks (1–32, default 12) in `columns` (1–8, default 3); `showUseButtons` controls use/equip actions for catalog items that support them. Players can drag stacks to reorder them or use the accessible up/down buttons; Sort applies a stable case-insensitive item-name order. Stack order feeds numbered item shortcuts and is retained in campaign progress. An authored inventory grid replaces the default standalone summary row. Panels may contain nested panels or widgets up to four levels deep and arrange children freely or in a row/column flow. `visibleWhenTab: { groupId, tabId }` shows a widget only on that page; each group selects one page, defaulting to its first authored tab. The optional `visibleWhen` uses one existing rule comparison against a scene/campaign variable or inventory count, and `visibleWhenPaused` can select paused or playing UI; these conditions combine. Widget order is draw order. The same saved scene field renders in editor Play and standalone exports, and the HUD editor writes this contract. No scripts or arbitrary HTML are accepted. Older scenes without `hud` remain valid.

An `event-button` with `eventId: "start-game"` dispatches `ui` rules whose `eventId` matches, so multiple scene nodes can respond to one button. Example listener: `{ "event": "ui", "eventId": "start-game", "actions": [{ "type": "set", "variable": "started", "value": 1 }] }`. Existing bounded rule conditions/actions still apply; no arbitrary code runs. `viewport_observe` step input and `playtest_run` step input accept `uiEventId`, sent once even in a multi-frame step. Viewport steps also accept `uiTab: { groupId, tabId }` to select a defined tab before capture; the response reports current selections in `observation.hudTabs`. `togglePause` is also a direct HUD action. `viewport_observe` and `playtest_run` accept `input.togglePause: true` as a one-shot pause/resume input, and playtests can assert `{ "type": "paused", "equals": boolean }`. Pause freezes fixed-step simulation and gameplay input while keeping rendering and HUD state active; authored UI events still run while paused so menus can work. Standalone touch exports retain a Pause/Resume button and hide gameplay controls while paused. Pause state is transient and is not saved in campaign progress.

`world.create` stores a seeded terrain descriptor with integer grid coordinates, a per-world `voxelSize` in meters per cell, storage chunk size `1..32`, finite horizontal bounds and vertical bounds. Generator `mode` can be omitted or set to `"heightfield"` for the original terrain path, or set to `"voxel3d"` for deterministic 3D occupancy with one finite cave passage and an optional cave field. `caveDensity` controls the seeded field; where that field reaches within three cells of the surface, it creates up to `caveEntrancesPerRegion` separated 3×3 mouths per 256×256 logical-cell region (default one, maximum four). Far and horizon terrain retain bounded mouth floors, while distant relief remains a heightfield approximation. Only caves reaching the surface cap open a mouth; `caveDensity` does not guarantee that all voids join one traversable network. With `caveNetwork` enabled, `caveNetworkReach` (0–4096 terrain cells, default 256) controls the lateral reach from a generated mouth to the trunk; zero disables those links. The scene's nullable `worldId` selects its terrain; the Scene Settings panel can create a seeded terrain and attach it in one saved transaction. Asset and world cell sizes are independent. Generator `landformScale` is an optional size in meters that controls terrain noise frequency; without it, version-1 descriptors retain their previous noise frequency without a version change. `world.update` accepts a partial set of `name`, `seed`, `chunkSize`, `voxelSize` and terrain generator settings, including mode and a partial nested `palette`. It merges those settings into the existing descriptor, preserves its ID and sparse edits, and validates the complete merged world before the transaction commits. Invalid combined settings reject the whole batch. Updates are undoable and redoable with the normal project history. `world.edit` takes up to 10,000 unique cell positions per transaction. A non-null value places/replaces a cell; `null` stores a tombstone that removes a generated cell. These sparse overrides survive project save/restart and ProjectStore undo/redo.

Example operation pair:

```json
[
  {
    "type": "world.create",
    "id": "island",
    "name": "Island",
    "seed": 42,
    "chunkSize": 16,
    "voxelSize": 0.5,
    "generator": {
      "type": "terrain",
      "version": 1,
      "origin": [-512, -512],
      "size": [1024, 1024],
      "minY": -64,
      "maxY": 256,
      "baseHeight": 36,
      "amplitude": 48,
      "noise": 0.25,
      "landformScale": 96,
      "palette": {
        "surface": 5614148,
        "subsurface": 7492665,
        "deep": 6843248,
        "surfaceDepth": 3,
        "subsurfaceDepth": 4,
        "materialType": "STANDARD"
      }
    }
  },
  {
    "type": "world.edit",
    "worldId": "island",
    "edits": [
      { "x": 20, "y": 37, "z": 14, "value": { "color": 16711680, "materialType": "EMISSIVE" } },
      { "x": 20, "y": 36, "z": 14, "value": null }
    ]
  }
]
```

To adjust the existing descriptor later, submit a partial update; omitted generator and palette settings keep their current values:

```json
{
  "type": "world.update",
  "worldId": "island",
  "name": "Expanded island",
  "seed": 314,
  "chunkSize": 16,
  "voxelSize": 0.25,
  "generator": {
    "amplitude": 56,
    "landformScale": 128,
    "palette": { "surfaceDepth": 4 }
  }
}
```

The 1,024×1,024 descriptor above covers one million surface columns; its vertical range defines a larger possible 3D cell lattice. Both are address-space bounds, not resident or rendered counts. The default heightfield path keeps bounded 5×5 windows at 1×, 2×, 4× and 16× cell spacing (25 slots per tier, 100 maximum) and builds at most one tile mesh per render update. The optional `generator.mode: "voxel3d"` uses seeded 3D density, one finite cave passage with a deterministic 3×3 surface shaft, greedy opaque faces, sparse cell overrides and a bounded 3×3×3 local chunk window (27 maximum). The same world keeps the existing heightfield tiers for distant silhouettes; horizon tiles preserve up to 32 edited or generated surface-opening cells across at most four coarse cells per tile using a bounded source-cell subgrid and a shared per-tile geometry-buffer cap; sampled far/horizon cave shells now show coarse interior cavity boundaries, though full distant volumetric LOD and overhang undersides remain absent. Omitted mode remains the compatible heightfield path. Scene Settings can select either representation. In simulation, actors and rigid bodies sample generated and sparse-edited 3D occupancy for voxel3d AABB collision; bounded leading-face queries can traverse the generated entrance, land on the voxel cave floor and block at cave walls. This does not provide general-purpose physics or a navigation mesh; voxel3d enemy chases use a separate bounded 3D A* route checked against actor-box occupancy. An oversized collider query conservatively blocks when it exceeds the 4,096-cell cap. In the editor, heightfield tiles and nearby voxel3d chunks can each be built one at a time in module Workers, with transferred geometry installed on the main thread and a synchronous fallback if worker setup fails. Changed resident voxel chunks rebuild through the voxel Worker, including adjacent face-sharing chunks; changed distant silhouettes refresh in place. Standalone exports retain bounded synchronous generation and rebuilding, processing at most one tile or chunk per update. Performance depends on target hardware and project content; these geometry and residency bounds do not guarantee a particular frame rate. Worlds support a `0.001..100` meter cell size independently of asset voxel size and scene-node scale.

Limits include 256 operations per transaction, 1,000 assets, 100 scenes, 5,000 nodes per scene, 250,000 voxels per asset and one million per project document. Recipes allow 256 shapes and four million cell evaluations. These document limits are current authoring guards, not a limit or performance claim for a future streamed world whose total population can exceed resident memory. The HTTP request limit is 25 MiB, so a document below a count limit can still exceed its serialized request-size limit. These are upper bounds, not performance guarantees.

Generation shapes support add/subtract/paint over boxes, ellipsoids, vertical cylinders, solid ramps that rise toward local +X, and deterministic seeded terrain. Box, ellipsoid, cylinder and ramp shapes accept optional Euler XYZ rotation `[x, y, z]` in radians around the shape center; each angle is bounded to `-2π..2π`. Terrain rotation is rejected. Omitted or zero rotation preserves the original voxel output. Rotated primitives are inverse-sampled inside their rotated AABB, and AABB cells count toward the existing four-million evaluation cap. Terrain uses normalized four-octave simplex noise; an optional palette assigns configurable surface, subsurface and deep colors by distance below each column's top. Later shapes override earlier cells. Regeneration requires a new ID so it cannot silently erase sculpt edits.

## Rigs and equipment

Rig definitions contain profile/version, named joints with parent and absolute bind positions, landmarks, sockets and clips. Bind and socket coordinates use asset grid units. A voxel can have up to four named weights summing to one. A socket's transform is local to its joint. Optional socket `fitBounds` supplies a meter-space box relative to that socket, before its scale. Scene attachment position overrides are meters; rotation is radians; scale is a multiplier. Socket attachments retain the attached asset's own meter-per-voxel size even when the wearer's asset uses a different voxel size.

Clips have duration, loop, authored locomotion speed, named joint tracks and timed events. The rig inspector edits marker names and times directly, keeps events time-ordered, and bounds edits to the clip duration and schema limit; advanced rig JSON remains available for landmarks and bulk edits. Runtime playback scales locomotion to movement speed. Marker events can drive version-1 rules with `event: "animation"` and an optional `marker` filter; the visual rule editor exposes this filter and an empty value matches every marker. Geometry optimization retains faces between regions with different skinning so motion can expose those surfaces.

The Rig Editor can add editable `idle`, `walk`, `run`, `jump`, `attack` and `wave` starter clips. `asset.character` biped and machine starters include shoulder, forearm, hand, thigh, knee and foot joints with separate voxel assignments; quadruped starters split each leg into upper leg, knee and foot joints. All generated families include idle, walk and run clips; quadrupeds use diagonal front/back timing. `project_apply` accepts `{ "type": "asset.animation-preset", "assetId": "…", "preset": "walk", "clipName": "…", "duration": 0.9, "intensity": 1 }`; `clipName`, `duration` and `intensity` are optional. Presets map common joint names and mirrored sides, including articulated lower legs and feet, and their generated tracks, markers and interpolation remain editable. Keys may set `interpolation` to `linear`, `smooth` or `step`; omitted values preserve the legacy linear behavior. Each clip has an editable `blendIn` duration from 0 to 2 seconds (default 0.12) that crossfades from the current pose when the clip starts; use 0 for an immediate switch. Older clips receive the default on schema load. The Rig Editor preview provides orbit, zoom, playback-speed and timeline controls. A player's `sprintMultiplier` (1–4, default runtime value 1.6) scales movement while sprint is held. The animation component can set an optional `running` clip name; while sprinting and moving, runtime uses it, or the conventional `run` clip if present, then falls back to the configured moving clip. Optional `jumping` and `attacking` clip names bind one-shot actions, which return to idle or movement after completion.

The initial equipment fitter requires `torsoMin`/`torsoMax` landmarks. Body shells share the selected body rig and hide a declared body region; backpacks and blades attach rigidly to sockets. Equipment declares the exact body it was fitted against. For manual arbitrary fitting, the Node Inspector can attach any untagged custom asset to a named body socket and edit its position in meters, Euler rotation in radians and positive per-axis scale (0.001–1,000); these offsets combine with the joint-local socket transform. For automatic preserve-shape fit, author socket `fitBounds` and use **Auto-fit to socket bounds** or apply `{ "type": "node.fit-attachment", "sceneId": "…", "nodeId": "…", "slot": "…" }` through `project_apply`. It computes one uniform scale and position from the asset's rest-pose voxel bounds, preserving its source voxels, rig, weights, current rotation and meter-per-voxel size. Rigged gear stays attached to the selected socket with its own skeleton and weights; to animate it with the wearer, provide a matching clip or retarget one onto the gear with an explicit joint map. This transform-only fit does not merge skeletons, remap weights or constrain animated deformation to the fit box.

## Multiplayer transport v1

The local broker exposes room management at `GET /api/multiplayer/rooms`, `POST /api/multiplayer/rooms` with `{ "maxPlayers": 16 }` (optional, 1–128), and `DELETE /api/multiplayer/rooms/:gameId`. These routes require `X-VoxShop-Token`. Room creation returns a generated `gameId`, a 256-bit base64url `credential`, the capacity and `websocketUrl`; the credential is returned once and only its SHA-256 hash is retained in the validated, atomic app-data state file. `GET` lists room IDs, active `playerCount` and `reservedPlayerCount` seats held for reconnect, without secrets. Creation may also provide `projectBinding: { projectId, revision, sceneId }`. For a bound room, the broker verifies the saved project revision, scene and player component, stores a private project snapshot, and starts a server-authoritative game simulation. Unbound rooms remain transport rooms without a game simulation.

The separate WebSocket endpoint defaults to `ws://127.0.0.1:4270/multiplayer` and accepts a first frame shaped as `{ "version": 1, "type": "join", "gameId": "…", "credential": "…" }`. A successful join returns the server-assigned `playerId`. Clients may opt into reconnect by sending `reconnect: true`; the `joined` reply then also carries a per-player `resumeCredential` and `nextInputSequence`. Store the resume credential securely and send it with the room credential on the next join to reclaim the same player identity. A successful resume rotates the credential, rejects replay of the previous value, preserves sequence monotonicity and sends the latest published snapshot when one exists. Unexpected disconnects reserve the player's seat for 60 seconds and discard any accepted input that has not yet been handed to a host tick. After expiry, the prior resume credential is invalid and a new join receives a new player identity. Clients that omit `reconnect` receive the original `joined` shape and permanently leave on disconnect. Input messages contain bounded movement/look/jump/interact/attack/use-item intentions; a `queued` response means the intention entered the host queue, while `ack` is sent only after the host commits a tick. Invalid credentials are rejected before a seat is allocated. WebSocket frames are limited to 4 KiB, rooms to 128 per process, seats to 128 per room, and queued inputs to 64 per player. The gateway sends heartbeats every 15 seconds by default and terminates sockets that do not answer a ping before the next check. The runtime `MultiplayerClient` keeps its rotating resume credential in memory and automatically retries unexpected transport loss with exponential backoff from 250 ms to 10 seconds; terminal join errors for unknown rooms, invalid credentials/messages or full rooms stop retries, and explicit `leave()` cancels retries and discards the saved resume credential. Reloading the page loses the in-memory credential.

Unbound rooms use the host simulation bridge: `POST /api/multiplayer/rooms/:gameId/tick/start` with `{ "serverTick": n }` drains accepted intentions once, followed by `POST /api/multiplayer/rooms/:gameId/tick/commit` with `{ "serverTick": n, "players": [...] }` after the simulation has applied them. Commit validates server-owned player snapshots and broadcasts acknowledgements and the snapshot. Ticks must increase and each start must be committed before another begins; both routes use the broker token. A project-bound room rejects these manual tick routes and advances its one shared `GameSimulation` on the host at the fixed-step tick schedule. Every connected client receives ordered authoritative game snapshots and sends only gameplay intentions; editor Play and standalone exports apply the same snapshot contract.

For bound rooms, `projectBinding.sceneId` is the entry scene. Snapshot `entrySceneId` stays set to that value while `sceneId` tracks the current scene; authored transitions may move the shared simulation only to scenes reachable from the bound entry scene. The first snapshot is accepted only when project ID, revision and entry scene match the joining game. Studio can create a bound room and choose **Play this room**; standalone exports expose endpoint, room ID and credential fields with Join/Leave controls. Progress save, load, export, import and restart controls are disabled while connected to a room. The exported game clears the entered room credential after joining, and the client retains its resume credential in memory only.

Room credentials and resume hashes, reconnectable player sequences, room bindings, the saved bound-project snapshot and the latest published snapshot persist under app data (`multiplayer-rooms.json` and `multiplayer-projects/`). A bound snapshot includes the current scene and authoritative game state, so the host can resume from it after restart. Live connections and queued, uncommitted inputs do not persist. Writes coalesce for up to 250 ms and graceful shutdown flushes; room creation/deletion flush before the REST response. On restart, active reconnectable players get a fresh 60-second recovery window, while already disconnected players keep their saved expiry. Corrupt state fails startup without overwriting the file. The gateway binds loopback unless certificate/key files and an advertised host are configured for TLS; remote operators manage certificates and network exposure themselves. The engine does not provide a public relay or matchmaking service.

## Gameplay API v1

Components: `player`, `combat`, `collider`, `interactable`, `rigid-body`, `collectible`, `inventory`, `construction`, `gate`, `health`, `enemy`, `patrol`, `animation`, `rules`.

The `player` component exposes `jump` strength, `gravity` (default 18 m/s²), `terminalVelocity` (default 50 m/s) and `stepHeight` (0–5 m; omitted/0 disables stepping). Optional `coyoteTime` and `jumpBuffer` windows each accept 0–0.5 seconds and default to 0, preserving immediate grounded-jump behavior unless enabled. Grounded players may step onto colliders or voxel cells up to the authored height, when the raised body fits and stays within world bounds. An explicitly solid `collider.shape: "capsule"` opts a player into swept capsule movement in Rapier-enabled runtimes; `maxSlopeAngle` accepts 0–89 degrees and defaults to 45. Its step-up also checks overhead clearance. Legacy/non-capsule actors and builds without Rapier keep the axis-separated AABB movement. The editor inspector and shared MCP project schema expose these values; buffered or coyote jumps consume one rising-edge press.

`combat` is optional and belongs on the player. It accepts `damage` (0.01–10,000, default 25), `range` in meters (0.01–100, default 3) and `cooldown` in seconds (0–60, default 0.35). A rising-edge attack damages every enabled enemy whose world position is inside the configured range. Existing projects without `combat` keep the original 25 damage, 3 m range and 0.35 second cooldown. The player inspector exposes these fields, and campaign checkpoints preserve an active configured cooldown.

The `interactable` component accepts `prompt`, `range` and optional `requiresLineOfSight` (default `false`). When enabled, the runtime hides a target if the segment from the player collider center to the target bounds center intersects another solid collider AABB or occupied terrain cell. The terrain walk is bounded to 4,096 cells per candidate and treats a ray beyond that budget as blocked; collider shapes use their transformed AABBs for this interaction query. The Node Inspector exposes the toggle, and older projects retain their previous nearest-target behavior.

Rules listen for `start`, `interact`, `touch`, `untouch`, `collision`, `separation`, `signal`, `tick`, `destroyed`, `attack` or `animation`. Player `touch`/`untouch` use the runtime's AABB overlap test and remain available without Rapier. Rapier-backed `collision`/`separation` rules report collider-pair entry and exit, including sensor intersections; both nodes need colliders, and the scene needs a dynamic rigid body for these events to be generated. Sensor colliders, including dynamic sensor bodies, report overlap without blocking motion. The event log records each participating node and the counterpart as `data.otherNodeId`. These physics events currently rely on Rapier's collision event pipeline: kinematic bodies crossing fixed sensors do not emit events in the tested Rapier 0.21 runtime, so use player `touch`/`untouch` for player triggers. Disabled participants' queued events are ignored. Rules can run once, use a tick interval, and compare a numeric scene variable or an inventory count with `>=`, `<=`, `==`, `>` or `<`. A comparison uses either `{ variable, op, value }` (finite numeric value) or `{ itemId, op, value }` (integer 0–1,000,000). Inventory counts sum all matching stacks in the player's inventory; the catalog item must exist in that scene. Keep the legacy `condition` field for one comparison, or use `conditionGroup: { mode: 'all' | 'any', conditions: [...] }` for one to eight comparisons: `all` requires every comparison to pass, while `any` requires at least one. Groups cannot nest and cannot coexist with `condition`. A failed condition skips the rule without consuming its once flag.

Actions: `set`, `add`, `destroy`, `enable`, `message`, `win`, `lose`, `damage`, `heal`, `teleport`, `craft`, `inventory`, `sound`, `audio`, `spawn`, `emit`, `transition`. A transition names a destination `sceneId`; project validation rejects missing destinations. A sound action is `{ "type": "sound", "waveform": "sine" | "square" | "triangle" | "sawtooth", "frequency": 20..4000, "endFrequency"?: 20..4000, "duration": 0.02..2, "volume": 0..1 }`; it plays a short procedural oscillator cue. An imported clip action is `{ "type": "audio", "clipId": "bell", "volume": 0..1 }` and plays the referenced project clip once. Projects embed clips as base64 data URLs, capped at 3 MiB each, 16 clips and 12 MiB total. `audio.put` and `audio.delete` edit this library; deleting a referenced clip is rejected. Scene music uses optional `music: { clipId, volume }` and loops while that scene is active. HTML media playback may wait for a user gesture when the browser or desktop WebView restricts autoplay. Standalone export includes only clips referenced by reachable scenes and prefabs. Actions are bounded to 4,096 per simulation step. This deliberately scoped language is the first custom-logic extension API. It provides no network, filesystem, shell or arbitrary evaluation capability.

`spawn` clones a saved prefab during play: `{ "type": "spawn", "prefabId": "guard", "offset": [2, 0, 0], "rotation": [0, 1.57, 0], "scale": [1, 1.5, 1] }`. `offset` is relative to the rule owner's world position; alternatively `position` sets an absolute world location. Use one placement field, not both. Optional `rotation` (Euler radians) and positive `scale` override the prefab root while leaving child transforms intact; omitted values inherit the saved root. Runtime IDs are generated, internal subtree targets are remapped, and each new node receives its normal component behavior and `start` rules. Spawned prefabs are not allowed to contain a player controller. Per scene, runtime spawning is bounded to 1,000 prefab instances and 5,000 spawned nodes; exceeding either limit makes that action fail and leaves a once rule retryable. Checkpoints store the root transform, template signature, prefab reference and runtime IDs alongside ordinary transforms, health and physics state; older checkpoints without root rotation/scale remain readable. Removing or changing a referenced template invalidates that checkpoint, so play starts from the authored scene. Standalone export recursively follows spawn actions in reachable scenes and prefabs, retaining only required prefab definitions and assets.

For `collision` and `separation` rules, `destroy`, `damage`, `heal` and `teleport` may use the reserved target `"$other"` to address the other node in the current Rapier collider pair. It resolves separately for each participant's rule dispatch; the target is invalid for other event types. The rule editor clears it when the event changes away from collision/separation. Ordinary node targets remain stable-ID references.

`heal` uses the same positive amount bound as `damage` (up to 10,000) and targets this object by default or a selected scene node. It changes health only on enabled nodes with a `health` component and caps the result at that component's authored maximum; a valid non-health target is left unchanged.

### Named gameplay signals

Rules can listen for `{ "event": "signal", "eventId": "door-open" }`, and an `emit` action queues `{ "type": "emit", "eventId": "door-open" }`. After the active rule and pending spawned start rules finish, the runtime delivers queued signals in order to enabled nodes with matching signal rules; a listener can emit another signal to compose gameplay across nodes. Delivery is iterative, not recursive, and consumes the same 4,096-action budget as other rule actions. If a cycle exceeds that budget, Play records an error and stops. Signal IDs use the shared stable-ID validation and are exposed through the project schema, MCP and Rule Editor.

### Player control bindings

The `player` component accepts an optional `controls` object, so exported games can choose their keyboard and gamepad layout instead of being tied to WASD. Older projects that omit it keep the existing defaults, including Shift for sprint, Escape for pause/resume and gamepad Start (button 9); gamepad sprint is unbound until configured. In the object inspector, expand **Keyboard, gamepad and touch controls** to capture keys, select gamepad buttons and assign stick axes; **Restore default controls** resets only that player's map. Keyboard values are `KeyboardEvent.code` arrays (up to four alternatives per action, exactly nine inventory-slot keys). Gamepad action values are button-index arrays; movement's D-pad directions each use one button index or `null` to disable that direction. Standard-mapped controllers use their standard layout; unmapped controllers expose raw button indices so their buttons can be remapped. Each movement/look axis accepts `{ axis: 0..15 | null, inverted: boolean }`; defaults map axes 0/1 to movement and 2/3 to camera look, and legacy controls receive those defaults. Unsupported key codes, out-of-range button or axis indices and duplicate button assignments are rejected when the project is validated. Agent `viewport_observe` step inputs and `playtest_run` steps accept optional `sprint: boolean` for repeatable testing.

Player camera styles are `first-person`, `third-person` and `top-down`. First-person uses an optional `cameraHeight` in meters (default 1.6) and hides the player's body to keep it out of the view; use right-mouse drag, touch drag or the configured look axes to look. Movement remains camera-relative; D-pad directions, gamepad action buttons, axis indices and axis inversion can all be remapped. Touch movement supplies a vector directly, and touch buttons invoke gameplay actions rather than synthesizing keyboard presses, so exported mobile controls keep working after key remapping. Keyboard inventory shortcuts use the authored nine slot keys; the gamepad and touch item buttons use the first usable inventory stack. Exported instructions are generated from each scene player's saved bindings.

For MCP, include `controls` in the player's component inside the usual revisioned `node.put` operation. The JSON shape is:

```json
{
  "type": "player",
  "style": "first-person",
  "speed": 3,
  "cameraHeight": 1.6,
  "controls": {
    "keyboard": { "moveForward": ["KeyI", "ArrowUp"], "jump": ["KeyJ"] },
    "gamepad": {
      "moveForward": 12,
      "jump": [0],
      "axes": {
        "moveX": { "axis": 0, "inverted": false },
        "moveY": { "axis": 1, "inverted": false },
        "lookX": { "axis": 2, "inverted": false },
        "lookY": { "axis": 3, "inverted": false }
      }
    }
  }
}
```

Unspecified bindings fill from the standard defaults. A key or button cannot drive two actions in the same player map; change the conflicting binding or set the gamepad action's list to `[]` / D-pad direction to `null` to unassign it. Set an axis's `axis` to `null` to leave it unused; repeated axis indices are allowed for intentional shared input.

Each scene can store up to 128 item definitions and 128 recipes. Items have an ID, name, optional description (up to 500 characters), stack limit (1–999, default 99), and one optional use effect: `heal` with an amount from 0.01–10,000, or `equip` with the ID of gear fitted to that scene player's exact body asset. Healing restores up to the player's authored health maximum and consumes one item only when health increases. An equipment item stays in inventory and toggles its fitted gear in the matching shell, backpack or blade slot; equipping another asset of the same kind replaces it. The catalog editor offers compatible fitted assets, and project validation rejects missing or mismatched gear. The player's configured inventory-slot keys (default `1`–`9`) and the standalone contextual touch button use the selected usable inventory stack. Agents can send `input.useItem` with the stable item ID in `playtest_run` or viewport steps. Missing items and invalid use leave inventory unchanged. Dynamic attachments render through the shared node visual path and are included in standalone exports and campaign progress. A recipe has 1–16 ingredient rows and 1–16 output rows; each row refers to an item ID and a quantity from 1–9,999. Use the **Items & Recipes** scene catalog editor for manual authoring, or include `items` and `recipes` in the full scene record passed to `scene.put`. Catalog IDs must be unique within their type, and all recipe and item-pickup references must resolve. `scene.put` replaces the whole scene record, so inspect first and preserve the rest of the scene.

Add an `inventory` component to the player to set its slot limit (1–128, default 24). `collectible` can retain its legacy score behavior through `variable` and `amount`; to grant a catalog item instead, set `itemId` and optional `quantity` (1–9,999). A pickup that cannot fit remains in the scene. A `craft` rule action takes `recipeId` and optional batches (1–99, default 1); it consumes ingredients and grants outputs atomically, so a failed craft leaves the inventory unchanged.

An `inventory` action grants, consumes or exchanges catalog items without requiring a crafting recipe. Its `remove` and `add` lists default to empty and each allow up to 16 distinct item IDs with integer quantities 1–9,999; at least one list must contain an entry. All removed quantities must already be held, then additions must fit the stack/slot limits. Both lists commit together or neither changes the inventory. Removals can free slots for additions. The same item may appear in both lists, but the full removal cost is checked before adding the reward. Success emits `inventory-changed`; failure emits `inventory-failed` with a reason and displays feedback.

Actions execute in order. If `craft` or `inventory` fails, later actions in that rule stop and the rule's once flag remains available for the next matching event; tick retries still respect their interval. Earlier successful actions are retained, so put the transaction before rewards, messages, node changes or transitions. The entire action list is not one transaction. For example, this once-only interaction consumes a key before opening a door:

```json
{
  "event": "interact",
  "once": true,
  "actions": [
    { "type": "inventory", "remove": [{ "itemId": "door-key", "quantity": 1 }] },
    { "type": "enable", "target": "locked-door", "value": false },
    { "type": "message", "text": "The door is unlocked." }
  ]
}
```

Define `door-key` in the scene catalog and `locked-door` as an enabled solid scene node. Without a key, the player gets inventory feedback and the door stays closed. The same exchange primitive supports authored currency costs, shops, quest hand-ins and rewards; their surrounding UI and behavior remain authored gameplay.

### Player construction

Add a `construction` component to a player to configure terrain placement/removal permissions; the control map chooses the inputs (defaults B/X). `place` and `remove` default to true; `range` is physical reach in meters (greater than 0 through 100, default 6). `placeCost` and `removeYield` each default to an empty list and accept up to 16 distinct catalog item IDs with quantities 1–9,999. Place costs are consumed per successful cell placement; removal yields are granted per successfully removed cell. Both lists may be empty for creative building. The object inspector exposes these controls and catalog lists. Item renames preserve their references; removal yields participate in transition compatibility checks.

Optional `palette` contains up to 32 paint choices with unique `id`, `name`, integer RGB `color` and `materialType` (`STANDARD`, `METALLIC`, `GLASS` or `EMISSIVE`). The inspector adds, names, colors and removes these choices with native controls. During Play, choose paint from the HUD or use the player's configured cycle-paint key/button (default Q); the configured place key/button (default B) places the selected color/material. The first choice is the initial default. Selected paint is scene-local and survives Save/Load and scene revisits. Empty or absent palettes preserve surface-color placement. Palette IDs identify selection shortcuts; placed cells keep their existing color/material values and uniform per-cell costs/yields. The Construction starter includes grass, timber, metal, glass and emissive paint.

The runtime checks permissions, distance to the target cell and placement overlap with the player/enabled solid objects before committing costs. Positive-volume overlap is rejected; touching a face is allowed. Empty removals, occupied placements, out-of-bounds edits, missing costs and insufficient inventory space produce no world or inventory change. A full harvest inventory leaves the terrain cell intact. Construction-enabled scenes use canonical voxel occupancy for terrain collision in either generator mode, so mined interiors and overhangs do not remain invisibly solid. Construction uses the same runtime terrain deltas and campaign checkpoint as existing Play editing; Stop and fresh runs preserve the authored project. The fixed reward is authored per removed cell, irrespective of the cell's material; material-specific drops remain a future extension. Existing scenes without this component retain free terrain editing with the player's configured bindings (B/X by default).

For repeatable agent checks, each `playtest_run` step may include `terrainEdit: { x, y, z, value }` alongside `frames` and `input`. It attempts exactly one cell edit before advancing that step, through the same player construction validation as the rendered viewport. Coordinates are logical cells; `value` is null to remove, or `{ color, materialType }` to place. Optional `input.constructionPaint` selects a palette ID once before that step, and `construction-paint` assertions check its selected ID. Rendered viewport steps can combine this selection with `placeCell: true`; selection precedes placement. Explicit headless `terrainEdit.value` retains full color/material control. Use a `terrain-cell` assertion with the same x/y/z/value fields and an `inventory` assertion to verify both sides. Missing worlds and out-of-bounds cells fail terrain assertions even when expecting empty space. These checks establish simulation state; inspect actual Play frames when visual details matter.

Rule `set` and `add` actions, variable conditions and variable HUD bindings accept optional `scope: "campaign"`; omitted scope preserves scene-local behavior. Campaign variables are shared by the scene session, exposed by `GameSimulation.inspect()`, and saved in a bounded `campaignVariables` map of at most 256 finite numeric IDs in the campaign checkpoint. Existing version-1 campaign saves without this field load with an empty map.

Across scene transitions, campaign variables, inventory and player health carry over; destination health clamps to that player's authored maximum. Scene variables, node state, world edits, elapsed simulation time, once-rule flags and tick deadlines stay local and restore on re-entry, then current campaign state applies. `start` initializes a scene on its first visit; restoring a saved scene does not replay initialization. Tick deadlines use simulated seconds, so changing the simulation frequency does not change their remaining duration. For collectible, craft-output and inventory-action grant items that can cross a transition, the destination must define the same stable item ID and `maxStack`; slot capacity cannot shrink. Item display names/descriptions may differ. Editor Play remains temporary.

Standalone **Save** now captures the active scene and every visited scene as one version-1 campaign checkpoint. Its separate browser-local key includes project and exported entry-scene IDs, and it is capped at 2 MiB total, 100 scenes, and 256 KiB per scene. **Export save** downloads that bounded checkpoint as JSON; **Import save** validates the file against this game and its current scene content before storing it in the destination browser profile. This supports manual backup or transfer between profiles without automatic cloud sync. **Load** and page startup restore the saved active scene plus prior scenes together; **Restart fresh** returns to the authored entry without deleting the checkpoint. If no campaign checkpoint exists or its format is malformed, the game can read an intact entry-scene version-1 legacy save. That legacy key stays intact, and the next Save writes the campaign format. Legacy saves lack execution state and therefore cannot recover old once-rule/timer history.

Checkpoints retain variables, inventory, health, outcome, changed node transforms/enabled flags, supported runtime terrain deltas and optional execution state. Optional `motion` records retain actor vertical velocities and each rigid body's linear velocity, angular velocity and sleeping state. Restoring a jump continues its ascent/descent; moving and spinning bodies resume from the saved pose and motion. Each visited scene keeps its own motion. Physics startup retains incoming motion before replaying queued steps, so an immediate re-save does not reset it. Older version-1 saves without motion remain readable and start with authored body velocities and zero actor vertical velocity.

Optional `behavior` records retain each patrol's destination index, each rigged node's selected clip and clock, and remaining attack/damage cooldowns. Patrol and animation records are bounded to 5,000 entries each and checked against current patrol routes and selected rig clips before restoration; non-loop clocks cannot exceed their clip duration. Cooldowns cannot exceed the current runtime's attack/damage windows. A marker-triggered scene transition captures the advanced animation clock, preventing that marker from replaying immediately on return. Older saves without behavior use the first patrol target, fresh clip clocks and zero cooldowns.

Terrain restore replaces the live delta with the checkpoint delta over the authored world, removing edits made after that save and rebuilding occupancy/column caches. A checkpoint without terrain returns to authored terrain. Edit limits are checked against the authored base plus incoming edits; touched-cell accounting resets to accepted saved coordinates. Saved terrain data is detached from live cells, and restoration merges/sorts the batch once rather than rebuilding the world for every saved cell.

Scene IDs, catalog/health/node references, terrain signatures, rule references and motion references are validated against the current game before any campaign is restored; one incompatible scene rejects the whole checkpoint. Motion has at most 5,000 entries per record and finite velocity components within ±10,000 physical units per second. Sleeping state requires a dynamic body with sleep enabled and zero velocities; Rapier clears velocities when sleeping. Optional full Rapier checkpoints include the serialized world, body/collider mappings, contact phase and solver state. Restore requires the exact Rapier runtime version and matching physics topology; invalid or incompatible native state falls back to saved transforms and body motion. The WASM event queue is separate from the world snapshot and is cleared during restore. Per-scene progress remains capped at 256 KiB and campaigns at 2 MiB, so large native worlds can return `too-large`. Runtime terrain edits do not mutate the authored project. Storage is local to one origin/browser profile and does not sync between devices. Invalid or unavailable storage is reported without blocking a fresh run. Input edges and event history remain transient. The legacy physics fallback retains linear velocity but does not simulate angular motion or sleep.

In the object inspector, the visual API v1 rule editor supports event choice, run-once behavior, tick intervals, single or grouped variable/inventory conditions and common actions. Inventory actions expose catalog-based remove/add rows and quantities; craft actions select recipes and transition actions select another authored scene. Item renames in the catalog update rule conditions and both inventory lists; referenced items cannot be deleted. Damage and heal actions expose a target and amount control. Less-common actions remain editable through a schema-validated JSON fallback, and the **Advanced behaviors** editor remains available for full component JSON. Both forms update the same local scene draft; click **Apply object changes** to commit it.

The `survival` starter demonstrates these current contracts in an editable short loop: collect two wood bundles and a stone, approach a workbench, press E to craft a campfire kit, and reach the campsite. Its item catalog, recipe, pickups, station prompt and bounded rules can all be edited in the project. This starter demonstrates one small survival-flavored loop; it does not define the engine's genre scope.

Editor Play defaults to 60 fixed simulation steps per second; standalone exports use 240 Hz while active. Deterministic playtests call the same simulation with a bounded fixed delta. When a scene has rigid bodies, the runtime lazily loads Rapier 3D for authored box, sphere and capsule colliders, dynamic/fixed/kinematic bodies, body-to-body contact, friction, restitution, angular motion, sleep and continuous collision detection. A `joint` component connects two rigid-body nodes in the same scene with `jointType: "fixed" | "revolute" | "prismatic"`, local meter anchors, a nonzero local axis for hinges/sliders, and optional `[min, max]` limits (radians for hinges, meters for sliders). Scene validation checks both endpoints; prefab joints must connect bodies within the prefab, and instantiation remaps the internal node reference. Campaign Rapier checkpoints include joint handle mappings and retain older snapshots without them. Scenes without rigid bodies skip Rapier initialization and the editor skips downloading its lazy chunk; standalone exports choose a Rapier-free runtime when no reachable scene needs rigid bodies, and include embedded physics plus its Apache-2.0 notice when needed. Players with explicit box, sphere or capsule colliders use bounded Rapier shape sweeps with configurable slopes, steps and moving-platform carry. Legacy no-body scenes retain synchronous AABB movement; legacy players can use a default box sweep when another rigid body initializes Rapier. Rapier receives resident terrain colliders rather than a collider for the full world. Movement uses normalized input and bounded collision substeps; a selected finite terrain world supplies the horizontal play limits from its logical grid extents, while scenes without terrain use `scene.bounds`. Enemy chase follows a direct route when clear; otherwise it caches bounded X/Z paths around authored solid colliders and heightfield ascents above the lesser of world-cell size and half the actor height. That grid uses 0.5m cells, up to 512 expanded nodes and 4,096 cells. In `voxel3d` worlds, enemies use a bounded 3D grid checked against the same actor-box occupancy used by movement, with up to 2,048 expanded nodes and 32,768 grid cells; terrain edits invalidate these routes. Both modes pause on capped or unreachable searches until their target or navigation revision changes. Trigger rules and collectibles use intersection with the player's collider. Play mode operates on a cloned scene, and Stop reloads authored transforms and enabled state.

## Playtests

`playtest_run` accepts a scene ID, input steps and assertions. It can assert a stable objective ID's derived completion state with `{ "type": "objective", "objectiveId": "collect-crystals", "equals": true }`:

```json
{
  "projectId": "my-game",
  "sceneId": "main",
  "steps": [{ "frames": 120, "input": { "moveX": 1, "moveZ": 0 } }],
  "assertions": [
    { "type": "no-errors" },
    { "type": "variable", "name": "score", "minimum": 1 },
    { "type": "objective", "objectiveId": "collect-crystals", "equals": true }
  ]
}
```

Input fields: `moveX`, `moveZ` in -1..1, `jump`, `interact`, `attack` and `useItem` with a stable catalog item ID. Jump/interaction/attack/item use require a fresh input edge; release between repeated actions. Assertions support `status`, `variable` minimum, `position` near/tolerance, `enabled`, and `no-errors`, plus:

- `active-scene`: `equals` is the final scene ID.
- `inventory`: `itemId` and `equals` check the sum across matching stacks, from 0–1,000,000. An undefined catalog item fails even when checking zero.
- `equipment`: `nodeId`, `assetId` and `equipped` check whether a fitted asset is currently attached to that runtime node. Pair it with an inventory assertion when equipment should remain available after use. This is simulation state, not a visual fit check.
- `terrain-cell`: integer `x`, `y`, `z` and `value` compare the active world's logical cell with a color/material record or null for empty. Missing worlds and out-of-bounds coordinates fail.
- `health`: `nodeId` and at least one of `minimum`/`maximum` check an inclusive range (0–100,000). Equal bounds check exact health; a missing health component fails.
- `scene-path`: `equals` is the exact route of 1–64 scene IDs during this test run.
- `objective`: `objectiveId` selects one authored goal and `equals` checks whether its variable or inventory condition is complete. Missing objective IDs fail.

At most 18,000 frames run per scenario. Reports include entry/final scene IDs, the traversed route, active state, source revision, events, errors and elapsed time. Every assertion returns expected/actual values and a failure message when it fails. These checks run through the shared schema in the editor and MCP adapters. Playtest assertions report simulation state and do not capture a rendered view.

## Export and extension boundary

`game_build` starts at the selected entry scene and includes every scene reachable through authored transition actions, plus assets and terrain worlds referenced by those scenes. Unreachable scenes and unused assets/worlds are omitted; generation recipes, unused variants and editor drafts are stripped. Geometry, materials, joints, animation and attachments remain. Runtime code is bundled into the HTML; Three.js notices are included. No provider credentials, editor API connection, MCP or external asset/font URL is needed.

The standalone page exposes `window.VoxShopGame` API version 1 for creators' external harnesses: `inspect()` (including the active `sceneId`), `scenePath()`, bounded `step(input, frames)`, `restart()`, `saveProgress()`, `loadProgress()`, `performance()` and `measurePerformance(durationMs)`. Progress calls use the same bounded browser-local save used by the HUD and return a result/status instead of throwing when storage is unavailable or a save is invalid. `restart()` starts from the authored entry scene and does not erase per-scene saves. The new measurement accepts 1,000–30,000 ms (default 5,000) while standalone Play is active and unpaused. It samples cumulative renderer calls, main-thread wall time inside synchronous `renderer.render()` calls, and simulation steps over the same monotonic elapsed interval. The returned `rendererCallMsPerCall` is average call wall time for that sample; it can include a synchronous driver wait and is not GPU-completion time. `performance()` includes `rendererCallsPerSecond`, `rendererCallMsPerCall`, `simulationHz`, `renderLoop`, `frameIntervalMs`, `drawCalls` and `triangles`. The standalone HUD shows renderer calls/s, main-thread ms/render and simulation Hz. `rendererCallsPerSecond` counts regular-loop `renderer.render()` invocations; `drawCalls` counts Three.js draw submissions for its last rendered frame. Neither is GPU-completion time or monitor-presented FPS. `measurePerformance()` also enables asynchronous timer queries only for its requested interval. When the context supports `EXT_disjoint_timer_query_webgl2`, `gpu` reports completed elapsed-time samples around `renderer.render()` as `lastMs`, `p50Ms`, `p95Ms`, `maxMs`, `sampleCount`, `pending`, `capturing` and `disjointSamples`; unsupported contexts return `supported: false`. `performance()` exposes the most recent GPU summary and visual/query counters. `visuals.occlusion` reports registered and currently occluded batches, valid visible/occluded results, and cumulative suppressed instances. These values describe GPU elapsed time and culler activity, not monitor presentation or net speedup; compare repeated same-scene measurements on target hardware. Viewport observations also report `render.instances`, the number of authored scene nodes assigned an instance slot in shared `InstancedMesh` batches. That count is distinct from draw calls and logical voxel-cell counts; world descriptors may cover far more cells than the bounded terrain meshes currently resident near the viewer. The editor benchmark reports `animationFrameCallbacksPerSecond` from `requestAnimationFrame` callback intervals while rendering is active. It does not count renderer calls or frames presented by the monitor. These interfaces provide local gameplay control, not a privileged authoring API. Future features should extend the shared document, command and runtime contracts with migrations and validation, rather than introduce an agent-only shortcut.

The editor Play preview and standalone page expose the same frame-pacing controls: rendering is uncapped by default, or can be capped at 30, 60, 90, 120, 144, 165, 240 or 360 calls/s. The editor preference is saved under workspace data; standalone preferences use the browser profile per project. Uncapped active play schedules renderer work with `MessageChannel` tasks; capped active play waits against a monotonic `performance.now()` deadline using timers, so a target above the display refresh rate is not gated by `requestAnimationFrame`. Late callbacks skip missed deadlines instead of trying to catch up. The simulation remains fixed-step and independent. These settings control render-loop calls only: they do not set V-sync, change a native swap chain or measure GPU-completed/presented frames. In the Tauri shell, the renderer remains inside the platform WebView, which controls display presentation.

## Actual viewport observations

The local MCP transport exposes `viewport_clients` and `viewport_observe`. Select an editor client and supply a canonical `projectId`, `expectedRevision` and command. Commands are `capture`, `focus` (nodeId), `camera` (position/target), `play`, `stop`, `step` (frames/input), `sequence` (steps) and `benchmark` (30–300 frame samples through `frames`, with optional `occlusionCullingEnabled` for same-scene on/off comparisons; the previous setting is restored). Walkthrough `moveX`/`moveZ` inputs are world-plane axes, so agents can repeat the same route independent of camera yaw. `input.uiTab` selects an authored HUD page by its group and tab IDs; responses include the active `hudTabs`. Physical keyboard/gamepad movement follows the live follow-camera yaw. Walkthrough steps are limited to 600 frames per request; a sequence shares that combined budget. Successful responses include an actual viewport PNG and camera, resolution, draw/geometry counts and simulation state. Benchmark observations report `requestAnimationFrame` callback interval percentiles, `renderer.render()` invocation count and synchronous call-time totals/average, renderer identity, draw/triangle counts, culling/world stats, and asynchronous WebGL GPU elapsed-time percentiles when the extension is supported. `animationFrameCallbacksPerSecond` names callback cadence while rendering is active. The historical `averageFps` field remains a compatibility alias for callback cadence; `p95Ms` is the p95 callback interval. Renderer-call CPU time, GPU elapsed time, callback cadence and monitor-presented frames are distinct measurements; GPU samples may be unavailable or disjoint.

During Play, `viewport_observe` also accepts a bounded `physics-query` command with up to 16 read-only probes: raycasts; oriented box, sphere or capsule overlap queries; and box, sphere or capsule shape casts. A shape cast starts at a world-space position, follows a normalized direction for at most `maxDistance`, and returns the nearest active collider's node/source, travel distance, contact point and surface normal. `includeSensors` and `excludeNodeIds` filter candidates. Queries inspect the current Rapier collider set, including resident terrain colliders, and do not advance simulation; they treat targets as stationary for the query. The schema bounds dimensions, range and result count. Query latency has not been profiled, so do not issue large repeated batches as a per-frame gameplay API.

Agent-controlled Play pauses between commands. Manual keyboard input resumes ordinary gameplay. The broker rejects stale revisions, competing requests, incorrect responses and disconnected/timed-out editors. The editor refuses a walkthrough while unsaved sculpt recovery is pending. Viewport capture requires an attached editor with an available renderer.

### Optional voxel3d caves and overhangs

Optional integer `generator.caveDepth` positions the finite main passage below `baseHeight` in terrain cells. Zero or omission keeps the previous amplitude-based placement; positive values are capped at 256 and clamp the passage center inside the world's vertical bounds. The connected surface shaft follows the passage. Set `generator.caveCrossPassage: true` to add one bounded orthogonal cross-passage; omitted/false preserves existing version-1 world geometry. Optional `generator.caveBranchCount` accepts 0–4 deterministic side passages connected to the main tunnel; narrow worlds may fit fewer, and zero/omission preserves prior occupancy. When `caveDensity` is enabled, optional `generator.caveEntrancesPerRegion` accepts 0–4 deterministic 3×3 surface mouths per 256×256-cell region (default one); cave density and bounded candidate searches may yield fewer, and zero disables generated mouths. Far and horizon LOD retain their floors under a bounded aperture budget sized for four mouths per region. The seeded carving field does not guarantee that all of its voids form one traversable network. When `caveNetwork` is enabled, `caveNetworkReach` sets the 0–4096-cell lateral connector limit (default 256); zero disables generated mouth-to-trunk links. Scene Settings and partial `world.update` expose these controls.

`generator.overhangDensity` accepts an optional value from 0 to 1. When enabled in `voxel3d` mode, a seed-derived 3D field can add vertically connected cells above selected heightfield columns. Optional integer `generator.overhangMaxHeight` sets the cap from 1–64 terrain cells and defaults to the former eight-cell limit. The field also respects saved `maxY`; omitted or zero density preserves the prior terrain boundary. The local voxel sampler and far/horizon heightfield meshes share their highest silhouette sample. Optional overhangProfile values control vertical density; overhangFootprint accepts a rectangular 1–64 by 1–64 normalized mask over the world bounds (rows +Z, columns +X) and interpolates density horizontally. Optional overhangHeightMap uses the same bounded grid shape to set normalized column heights up to overhangMaxHeight, rounds to whole terrain cells, and takes precedence over procedural density, profile and footprint. Without the height map, prior seeded output is preserved. Scene Settings and partial world.update can set or clear these controls. Seeded noise still determines exact column edges unless the authored height map is set; that map controls columns at its grid resolution. Distant cave rendering now adds bounded sampled shells for interior voids; it is not full volumetric LOD, and overhang undersides remain unrepresented. Scene Settings and partial `world.update` expose these controls.
