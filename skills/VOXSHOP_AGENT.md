# Operate VoxShop through MCP

For current engine behavior, read [the shared engine guide](ENGINE_GUIDE.md) and [current limits](ENGINE_LIMITS.md), also exposed through MCP resources. Example games and current resource safeguards do not define the engine's long-term genre or world-size ceiling.

Use the running local VoxShop MCP server for the numbered workflow below. Do not edit `.voxshop/projects` directly or poll compatibility-worker files. Do not run shell commands or arbitrary code through a gameplay rule.

1. Call MCP `tools/list` on the connected transport and inspect the returned tool names and `inputSchema` fields before composing requests. The local stdio adapter exposes the complete operation union in `project_apply.inputSchema`. The hosted Sites adapter also exposes `project_commands`; call it there to read the transaction schema. On Sites, `asset_preview` returns SVG (local `preview_capture` returns PNG), `project_playtest` corresponds to `playtest_run`, and `scene_build` corresponds to `game_build`. The hosted adapter has no live viewport tools. Use only tools the connected server reports.
2. Call `project_list` and `project_inspect` using the discovered schemas. Choose the intended project. `project_activate` opens it in the editor. Use `project_inspect` with `compact: true` before changing anything; it includes scene nodes, components and world settings without large voxel arrays. Use `asset_inspect` with `offset`/`limit` to page selected voxels. Use `full: true` when you need the complete portable document; full takes precedence if both flags are true. Stable IDs identify entities; names are display labels.
3. Every mutation uses the current `expectedRevision` from the latest inspection or preceding mutation's `appliedRevision`, and a unique `requestId`. After a successful `project_apply`, use its returned `appliedRevision` for the next write and re-inspect to confirm before iterating. Repeat an identical request ID only when retrying identical arguments. On a revision conflict, inspect the newer project and reconcile the intended changes.
4. Use `asset_generate` for asynchronous composable solids, and `job_status`/`job_cancel` for its lifecycle. Use `project_apply` for atomic batches, including `asset.character`, `equipment.fit`, `asset.variant`, `asset.edit`, `node.put`, `scene.put`, `scene.scatter.create`, `scene.scatter.delete`, `prefab.put`, `prefab.instantiate` and `editor.set`. Scatter creates seeded ordinary nodes from a static opaque asset (up to 4,096 voxels); terrain snapping needs a world and in-world bounds. A prefab placement needs one new unique node ID per saved node in `prefab.nodes` order; placement remaps internal parent and rule-target IDs while preserving external scene/catalog references. A prefab with `attachmentParentId` requires that parent in the destination scene.
5. Preserve designated manual edits. Generate under a new asset ID or create a variant before regeneration. Assets are shared by reference across scene instances.
6. Inspect `asset_inspect` and its paged voxel data when needed. Call `preview_capture` for a real static isometric PNG. Check silhouette, materials and dimensions; the preview does not show animated equipment fit.
7. Place scene objects with asset IDs, full transforms and components. A node's parent must exist in the same scene. The entire batch is validated before saving, so dependent assets, nodes and rules may be authored together.
8. Configure rig profiles, landmarks, named sockets and compatible equipment. Generated wearables target the selected body ID. A shell uses compatible skinning; a backpack/blade uses a rigid socket. Do not claim that arbitrary clothing can fit any body.
9. Configure gameplay with supported components and version-1 event/action rules. For new logic, combine events, conditions and bounded actions. Rules on different nodes can compose through named events: listen with `{ event: "signal", eventId: "door-open" }` and emit with `{ type: "emit", eventId: "door-open" }`; delivery is queued, iterative and shares the 4,096-action per-step limit. Conditions can compare a variable or a catalog item's total inventory count. Scene `objectives` use the same condition contract and allow up to 16 stable `{id,text,condition}` records with optional same-scene `requires` objective IDs. Prerequisites must be acyclic; `inspect()` reports each objective's `current`, `available` and `completed` state. Objectives remain derived HUD progress, not separately saved data. Exploration, Arena and Survival starters demonstrate objective authoring; Construction stays open ended. `touch`/`untouch` report player AABB-overlap entry/exit; disabling the player or target clears contact silently, and these are not Rapier sensor events. Use `inventory` remove/add lists for grants, costs and atomic exchanges, and `craft` for recipes. Put these before success messages, rewards, node changes or transitions: failure stops later actions and leaves a once rule available to retry on its next matching event; earlier actions are retained. Never substitute unrestricted evaluation for a missing engine capability.
10. Run `playtest_run` with repeatable input steps and assertions. Input steps support optional `sprint` for authored run behavior. Inspect the discovered schema for `input.useItem` (stable item ID), objective completion by objective ID, inventory totals, equipped gear, health ranges, active scene and exact scene route as well as status/variables/position. For an equipment item, assert both that its fitted asset is equipped and that the inventory token remains; for a healing item, assert health gain and one-item consumption, while full health should consume nothing. Failure results include expected/actual values. Read the final job report. Static image previews and deterministic simulation tests do not prove rendering or human usability; inspect keyboard and touch Play in a browser when available.
11. Use `project_undo`/`project_redo` to reverse whole transactions. Revisions increase even when undoing. `project_save` produces a portable snapshot; ordinary accepted changes already save automatically.
12. Use `game_build` to export a scene. Read the job's artifact path, revision, hash and limits. It must play without the creating agent, editor service or AI connection. Report what was tested and any unsupported features honestly.

World counts describe logical cells; worlds and detailed assets can span millions of them. Seeded terrain stays a compact descriptor plus sparse edits, hydrated and meshed in bounded chunks. Use `world.create`/`world.update` for settings and `world.edit` for sparse overrides instead of enumerating generated cells. `world.voxelSize` is meters per terrain cell; `asset_generate.voxelSize` is meters per asset voxel. The heightfield stream reduces horizontal sample density and coarse vertical steps through bounded near, medium, far and horizon tiers. Optional `voxel3d` terrain adds a bounded local chunk window with one finite cave passage and shaft; distant terrain remains heightfield. With `caveNetwork` enabled, `caveNetworkReach` controls generated mouth-to-trunk links from 0–4,096 terrain cells (default 256; zero disables those links). Keep world and asset physical scales independent; inspect terrain from multiple distances when reviewing cave details and near/far transitions.

For a visual review through local stdio, use `viewport_clients` and `viewport_observe`. Select the open editor, supply the current project revision and use `capture`, `focus`, `camera`, `play`, `step`, `sequence` and `stop`. Step inputs accept `moveX`, `moveZ`, and optional held `sprint`, `jump`, `interact` and `attack` controls. Every successful observation returns a rendered PNG plus camera, resolution, draw calls, triangles and runtime state. Agent-driven Play pauses between bounded steps. Inspect several viewpoints and gameplay, including equipment and animation. If a problem appears, stop Play, reconcile the newest revision, make a focused edit, and inspect the same viewpoint and scenario again. Playtest assertions prove simulation behavior only, and draw-call/triangle counts are not FPS evidence. Hosted Sites may not provide live viewport tools, so check its discovered schemas or connect the local stdio adapter for editor camera and gameplay images. If no editor is attached, report that the visual review is unavailable.

`example_create` offers exploration, arena, survival crafting and construction starters. Exploration tracks its five-crystal goal, Arena exposes shell/sentinel goals, and Survival tracks gathering and building; Construction remains open ended. Construction includes 64 building blocks, a fitted character, a finite voxel world and editable cost/yield/reach controls. Survival demonstrates catalog pickups and an interactable workbench recipe. These are samples of current building blocks, not genre boundaries. For a project combining distinct modes, put each mode in its own scene and author through the operations, components and bounded rules in the discovered schemas. The project schema allows up to 100 scenes; each scene supports at most one player controller, and a standalone build starts at one scene and includes reachable transitions. These contracts do not promise systems absent from the current schemas.

Coordinate contract: project units are meters, Y up, rotations are radians. Voxel coordinates and rig bind positions are in asset grid units. Socket positions are relative to a joint in grid units; scene attachment position overrides are in meters. Scale is positive. Starter characters face -Z.

For player building, add `construction` to the player and set `place`/`remove` permissions, `range` in meters, `placeCost` and `removeYield` catalog rows. Empty lists enable free creative editing; rows apply per successful cell. The existing B/X controls use those settings and reject placement inside the player or enabled solid objects. Agent playtests can attempt a single `terrainEdit` before a step's frames and inspect it with `terrain-cell` assertions; pair them with inventory assertions to verify costs/rewards. These coordinates are logical terrain cells, independent of model voxel spacing. Save/resume retains inventory and terrain together. Full or missing inventory, range/permission failures and invalid/no-op targets must leave both unchanged. Inspect rendered gameplay separately.

Optional `construction.palette` contains up to 32 `{id, name, color, materialType}` paint choices. The inspector edits these choices; editor/standalone Play offers a native selector and Q cycles them with canvas focus. Runtime inspection exposes `construction.palette`, `selectedId` and `enabled`. Set `input.constructionPaint` once in a viewport/playtest step to select before that step's edits/frames; a rendered step can combine it with `placeCell`. A playtest `construction-paint` assertion checks its selected ID. Explicit headless `terrainEdit.value` keeps direct color/material control. Uniform cell costs/yields apply to every paint. Selection saves per scene; older saves and absent palettes keep their defaults.

For frame measurements, use the bounded `benchmark` command. Comparable static-scene samples can set `occlusionCullingEnabled` to `false` and `true`; the benchmark restores the previous setting. It separates animation-frame callback cadence, `renderer.render()` call count and synchronous CPU call time from asynchronous GPU elapsed-time samples when supported. GPU samples can be unavailable or disjoint, and these values do not report monitor-presented FPS. Display refresh and scheduling can cap callback cadence. Independently exported games offer visible creator walkthrough controls at `?voxshop-inspect=1`, with no broker required, plus `window.VoxShopGame.performance()` for renderer calls/s, simulation Hz, draw calls and triangles. `rendererCallsPerSecond` counts `renderer.render()` invocations, not GPU-completed or monitor-presented FPS.

If an agent does not show VoxShop tools, check the host's MCP status before changing the VoxShop setup: Claude Code supports `claude mcp list` and `/mcp`; Gemini CLI supports `gemini mcp list` and reports local stdio servers as disconnected when the current folder is untrusted; Codex supports `codex mcp list` and `/mcp`; OpenCode supports `opencode mcp list`. Desktop clients expose their own MCP status UI. Once the host reports a connection, call `tools/list` on that same client and inspect its returned schemas. These host checks diagnose configuration and trust; they do not establish editor viewport availability.

### Read-only physics probes

For read-only physics probes, inspect the connected MCP schema and call `viewport_observe` with `command: { type: "physics-query", queries: [...] }` while Play is active. A batch accepts 1–16 rays, oriented box/sphere/capsule overlaps, or box/sphere/capsule shape casts. Rays and casts return the nearest hit; casts also return travel distance, world-space contact point and surface normal. Overlaps return matching scene node IDs and terrain/environment sources. Optional filters can include sensors or exclude node IDs. Probes do not step simulation or modify project data; they inspect active Rapier colliders and only resident terrain chunks, not the entire generated world. Dimensions are bounded to 1,000 m, query distance to 10,000 m, and overlap results to 128. Shape casts treat targets as stationary and currently scan the active collider set. Use the returned `physicsQueries` observation; query latency is unmeasured, so do not use these probes as a per-frame gameplay API.
